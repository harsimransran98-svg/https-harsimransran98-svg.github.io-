How to Migrate a Chrome Extension from Manifest V2 to V3

Short answer

To migrate a Chrome extension to Manifest V3, set "manifest_version": 3, move the background page into a service worker, replace blocking webRequest with declarativeNetRequest, switch tabs.executeScript to chrome.scripting, and move host access into host_permissions. The biggest change is that background code no longer stays alive — anything that relied on in-memory state or timers has to be rewritten around events and chrome.storage.

Why migrate now

Chrome has phased out Manifest V2: MV2 extensions are switched off for everyday Chrome users and can no longer be published to the Chrome Web Store. Edge follows Chrome, and Firefox and Safari both support Manifest V3 as well, so one MV3 codebase is now the sensible base for every browser.

1. Update the manifest

  • Set "manifest_version": 3.
  • Rename browser_action / page_action to a single action.
  • Move site access (for example "https://*.example.com/*") out of permissions into host_permissions.
  • web_accessible_resources becomes a list of objects with resources and matches.
  • content_security_policy becomes an object (extension_pages, sandbox).

2. Turn the background page into a service worker

Replace "background": {"scripts": [...]} with "background": {"service_worker": "background.js"}. The worker starts when an event fires and is stopped when idle, so:

  • Register all listeners at the top level of the script, synchronously.
  • Keep state in chrome.storage (or storage.session for temporary data), not in global variables.
  • Use chrome.alarms instead of long setTimeout / setInterval timers.
  • There is no DOM in a service worker — use an offscreen document (chrome.offscreen) for things like clipboard access, audio or DOM parsing.

3. Replace blocking webRequest

Extensions that block or modify requests move to declarativeNetRequest: you declare rules (static rule sets in the manifest, or dynamic and session rules added at runtime) and the browser applies them. Observing requests with non-blocking webRequest still works.

4. Update script injection

chrome.tabs.executeScript and insertCSS are replaced by chrome.scripting.executeScript and chrome.scripting.insertCSS, which need the "scripting" permission. You inject a file or a function — not a string of code.

5. Remove remotely hosted code

Manifest V3 does not allow loading and running code from a server or using eval-style execution. Bundle every script inside the extension; fetch data (JSON, config) from your API instead of code.

6. Test, then submit

Load the unpacked extension, watch the service worker in chrome://extensions, and test what happens after the worker has been stopped and restarted — that is where most migration bugs hide. Then update the store listing, including permission justifications, and submit.

Questions

How long does a Manifest V3 migration take?

Small extensions can be migrated in a few days; extensions with heavy background logic or request blocking take longer because that code has to be redesigned around events and declarativeNetRequest.

Will my extension keep its users after migrating?

Yes. Publishing the MV3 version as an update to the same store listing keeps your users, ratings and extension ID.

Does Manifest V3 work on Firefox and Safari?

Yes, both support Manifest V3, with some differences in background scripts and API support — so plan the migration with all target browsers in mind.
